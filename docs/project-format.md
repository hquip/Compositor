# Compositor project format, versions 1–17

A `.comp` file is a macOS document package containing `manifest.json` and an `images/` directory of `<layer UUID>.png` assets.

The manifest identifies `com.compositor.project`, version `17` for new saves (versions `1`–`16` remain readable), and the sRGB display-cache space. It stores document UUID, pixel dimensions, active layer UUID, and layers in bottom-to-top order. Each layer stores its UUID, name, visibility, transform (origin, size, clockwise rotation, flips, sampling), and optional image filename. Blank layers have no image asset.

Version 17 adds `resources: [{ file, kind }]`, top-level and layer `workflow` dictionaries, and optional layer `fillOpacity` (finite 0–1, default 1). Resource filenames are `<UUID>.resource.bin`, under `images/`, with kinds `icc`, `channels`, `lookup`, `photoshop` or `plugin`. Resources are preserved byte-for-byte, included in archive budgets, and validated independently of display PNGs. ICC resources require an ICC signature; Photoshop sources require a PSD/PSB header. Lookup files are bounded to 32 MiB. JSON workflow data is limited by the existing 4 MiB manifest limit and 64 nested levels. Pre-17 readers reject these projects.

Authoritative channel resources start with `CCHN0001` (8 ASCII bytes), followed by little-endian u32 width, height, mode (0 RGB, 1 CMYK, 2 Lab), depth (8/16/32), channel count (4 RGB/Lab including alpha, 5 CMYK including alpha), and a reserved zero u32. Interleaved samples follow at offset 32. Integer samples are unsigned little-endian normalized values; float samples are IEEE float32 in their declared component units, with normalized alpha. Each resource is at most 16 MP. Floating samples must be finite within ±1,000,000 and alpha within 0–1. Workflow metadata identifies the channel source and embedded profile; ordinary PNGs remain the display cache. Opaque retained Photoshop/plugin data does not imply native editability.

Embedded PNGs preserve source pixels and transparency; transforms remain separate. Projects survive moving or deleting imported source photos. Saving uses a coordinated atomic package replacement. Unsupported versions, invalid metadata, missing assets, unsafe paths, and oversized data are rejected before replacing the live document.

Limits: 30,000 pixels per canvas/image side, 100 million total source pixels, 10,000 layers, 4 MiB manifest, 512 MiB per encoded asset. See `ProjectStore.swift` for validation.

Undo history and viewport are session-only. Opening fits the canvas, restores selection, and starts with clean history. Future editable features must extend the schema and round-trip tests. PNG export is a flattened derivative and does not mark project edits saved.

Image Size adds optional `resolution` (pixels/inch, 1–9600). Older manifests without it default to 72. This additive field retains version 1 compatibility. Both PNG and JPEG exports include document resolution metadata. Resampling stores the new layer pixels and bounds; undo retains the prior sources only during the current session.

Version 2 adds optional `parentID` and `isGroup` on layer records. A group has no image file. Root nodes have no parent; children refer to an existing group. Array order defines bottom-to-top sibling order; renderers traverse each group as a contiguous subtree. Visibility is inherited without changing child flags. Cycles, missing/non-group parents, image-bearing groups, and nesting beyond 64 ancestor levels are rejected. Group ancestors permit room for leaf nodes at the deepest level. Group metadata survives image/canvas resizing and cropping. Older app builds reject version 2 rather than misrender grouped documents. Collapse state is not serialized.

Version 3 adds optional per-layer `opacity` (finite 0–1) and `blendMode` (Normal, Multiply, Screen, Overlay, Darken, Lighten, Difference, Color Dodge, Color Burn). Missing fields default to full opacity and Normal. Group records required those defaults until version 8, which lets a folder carry its own opacity; a folder's opacity multiplies into every layer inside it, while its blend mode stays Normal because folders are pass-through. Effects are applied during compositing and retained as metadata when resizing sources. Files declaring older versions cannot contain non-default appearance values.

Version 4 adds optional `maskFile` and `maskEnabled` fields to individual layers. Mask filenames must be `<layer UUID>.mask.png` under `images/`; enabled defaults to true when a mask exists. Records without masks omit both fields. Groups cannot carry masks in this version. Files declaring versions 1–3 cannot contain mask metadata.

Masks store 8-bit grayscale coverage without alpha (white reveals, black hides). Their normalized extent matches the image’s local rectangle, so the same layer transform applies to both. A uniform 1×1 mask is valid and avoids allocating full-resolution pixels before painting. Nonuniform mask pixels and a thumbnail are immutable assets shared by history. Image Size resamples them with the image transform; Canvas Size and Crop preserve their pixels. Up to 100 million mask pixels may be stored in addition to the existing 100 million image pixels; per-side and per-file limits also apply to masks. Disabled masks remain embedded and editable but do not affect compositing. Image-versus-mask target selection is session-only and reopens on image pixels.

Version 5 adds optional `maskSourceID`: the UUID of a non-group layer supplying live alpha in document coordinates. It multiplies the target’s alpha alongside its enabled raster mask. Source pixels, transform, opacity, raster mask and upstream live masks contribute coverage; visibility and RGB color do not. Sources remain independent layers. Missing references, self-links, cycles, group endpoints and chains over 256 nodes are rejected. Deletion can bake the live coverage into dependent image pixels (retaining their raster masks) or remove the links, as one undoable operation. Links survive image/canvas resize and crop. Older versions default to no live mask; older app builds reject v5.

UI terminology: these alpha links are clipping masks. Option-click assigns the lower sibling’s base or releases the connection. Multiple clipped layers share one base, show indented above it, and release when moved outside the contiguous stack. The underlying `maskSourceID` representation is unchanged.

Version 6 allows `maskFile` and `maskEnabled` on group records. A folder has no image, so its mask covers the folder's own transform rectangle (the canvas size when the folder was created); Image Size resamples it through that transform, and Canvas Size and Crop preserve its pixels, exactly as for layer masks. Groups are pass-through, so an enabled folder mask multiplies the coverage of every descendant layer, together with that layer's own mask and any enclosing folders' masks; clipping-mask coverage is unaffected. Files declaring versions 1–5 cannot give a group a mask, and older app builds reject v6.

Version 7 adds adjustment layers: a layer record with an optional `adjustment` object and no `imageFile`. Adjustment layers cannot be groups and cannot carry `text`; like any layer they take a transform, opacity, blend mode, raster mask and clipping link, and they affect everything composited below them within their folder. `kind` is one of `Hue/Saturation`, `Levels`, `Curves`, `Exposure`, `Gradient Map`, `Grain`, `Invert`, `Black & White` and `Color Balance` (version 9 adds three more). The record carries the settings of every kind, each optional and defaulting to an identity adjustment: `hue` (±360), `saturation` and `lightness` (±100), `colorize` and `hsvSettings` for Hue/Saturation; `levels` (four channel ranges, RGB then red, green, blue); `curves` (four channel point lists); `exposureSettings`; `gradientMapSettings` (`shadows`, `highlights`, `reversed`); `grainSettings`; `blackWhiteSettings`; `colorBalanceSettings`. Out-of-range or non-finite values are rejected. Files declaring versions 1–6 cannot contain adjustment records, and older app builds reject v7. See `LayerAdjustment.swift` for the exact ranges.

Version 8 lets a folder carry its own `opacity`, which multiplies into every layer inside it; a folder's blend mode stays Normal because folders are pass-through (files declaring 1–7 require folders at full opacity). It also adds an optional top-level `guides` array of alignment guides, each with `id`, `axis` (`horizontal` or `vertical`) and `position` in document pixels (finite, at most 1,000,000 in magnitude). At most 1,000 guides are stored; files declaring 1–7 cannot contain guides. Guides survive Canvas Size and Crop by offsetting with the canvas.

Version 9 adds three adjustment kinds that sample neighboring pixels: `Gaussian Blur` (`blurRadius`, 0.1–250 document pixels), `Motion Blur` (`motionAngle`, −90 to 90 degrees, and `motionDistance`, 1–2000) and `Add Noise` (`noiseAmount`, 0.1–400, `noiseGaussian`, `noiseMonochromatic` and `noiseSeed`, so the pattern is stable between sessions). Files declaring 1–8 cannot contain these kinds; the earlier adjustment kinds remain valid at version 7 and up.

Version 10 lets a text layer color some of its letters differently: optional `colorRuns` in its `text` metadata (see Editable text). Files declaring 1–9 cannot contain it.

Version 11 lets those letters use different faces too: optional `fontRuns` in the same metadata. Files declaring 1–10 cannot contain it. `colorRuns` stays valid from version 10.

Version 12 adds editable filter stacks on pixel layers. `filterSourceFile` names `<layer UUID>.source.png`, an unmodified embedded PNG. `filters` is an ordered, nonempty list of at most 32 entries, each with a unique UUID `id`, Boolean `enabled`, and an `adjustment` object using the existing twelve `LayerAdjustment` kinds and parameter schemas. A stack requires an `imageFile` and cannot coexist with group, adjustment-layer, shape, or text metadata. The ordinary image asset is the rendered cache; unchanged opening and saving preserve its pixels. Editing the stack rerenders from the source. Pixel-changing operations bake the displayed pixels and remove the source reference and stack metadata. Geometry, masks, opacity, and blend changes retain them. Sources count toward the image-resource memory budget. Older clients reject version 12 rather than discard editable data.

Filter sources may be 8-bit or 16-bit PNGs; a 16-bit source consumes twice the source-pixel budget. The ordinary image cache and raster masks remain 8-bit. `filterWorkingSpace` optionally names one of `sRGB`, `Adobe RGB (1998)`, `Display P3`, or `ProPhoto RGB`; absent means sRGB. A high-precision source embeds its input ICC profile in PNG `iCCP`. High-precision filter calculations use the working profile, with an sRGB display cache, and profile-aware TIFF export can retain the 16-bit results. Pixel-editing tools in the shared editor require explicitly rasterizing a 16-bit source before replacing it with the displayed 8-bit pixels. Source/cache preservation on Mac remains separate from native high-precision editing support.

### Additive layer fields

Version 15 adds protected raster smart objects and float32 HDR originals. Optional `smartObject` is `{ id, width, height, baseTransform }`, with a UUID, original-source dimensions, and a validated layer transform for Reset. It requires an ordinary `imageFile` cache plus either `filterSourceFile` or `hdrSourceFile` and the editable filter list. It cannot coexist with group, adjustment-layer, text, shape or vector-path metadata. Width/height must match the embedded original. Copies retain the object UUID and updates replace the sources of shared copies within the same project; Make independent assigns another UUID. Pixel edits require explicitly rasterizing the object or editing its content tab. The content is embedded raster data, not a saved nested layer tree.

An HDR layer names `<layer UUID>.hdr-source.tif`. Its cache remains an eight-bit PNG; its immutable original is a canonical little-endian, uncompressed classic TIFF, single RGBA image/strip, 32 bits/sample, IEEE float samples (`SampleFormat=3`), RGB photometric mode, unassociated alpha, top-left orientation, and ImageDescription `Compositor linear sRGB float32\0`. RGB samples are finite in −1,000,000…1,000,000; alpha is finite in 0–1. At most 16 MP is allowed in a stored HDR surface. It cannot coexist with `filterSourceFile`; its nonempty filter list uses the existing filter-record schema. Each HDR source pixel consumes four resource-budget units. TIFF bytes remain unchanged during transport, opening, transformations, masks and preview changes. Native Mac source preserves the raw TIFF and filter/mask metadata without converting it to a PNG source.

Optional top-level `hdrView` is `{ exposure, toneMap }`: finite exposure −20…20 stops and `Reinhard` or `Clip`. It changes SDR display mapping; float source and export values remain unchanged. HDR image/filter/composite data uses linear sRGB; its source values are not bounded to 0–1. Supported filters and blends are described in [smart objects and HDR](smart-hdr.md). Reader gates prevent versions 1–14 from carrying these fields. Old readers reject new version-15 saves.

Preview 0.9.0 [OpenEXR import/export](openexr.md) adds no serialized fields or asset types. Input alpha and linear color conversion normalize selected EXR channels into the existing canonical linear-sRGB TIFF; data/display-window placement uses the existing canvas dimensions and layer transform. The original EXR container is not embedded. Project format and `ProjectManifest.current` remain 15.

Version 16 adds optional document `hdrWorkingSpace`: `Linear sRGB`, `Linear Rec.2020`, `Linear P3-D65`, `ACEScg` or `ACES2065-1`. Missing defaults to linear sRGB. The top-level `colorSpace: sRGB` still describes SDR images/caches. Canonical HDR TIFF sources may use any listed linear space, identified by ImageDescription `Compositor <space> float32\0`; the original sRGB description keeps its spelling `Compositor linear sRGB float32\0`. These wide-gamut descriptions require version 16. HDR source pixels remain unassociated RGBA32 float; source space can differ from the document composite space, and conversion does not rewrite the immutable source. Individual editable filter stacks retain their source space; document adjustment layers use the composite space.

Optional `hdrView.displayMode` is `Auto`, `HDR` or `SDR` and requires version 16. Auto/HDR request an extended HDR display on capable devices; unavailable display/API capability uses the SDR tone-map fallback. Display settings do not alter saved float sources or exported radiance.

An HDR layer may additionally retain `exrSourceFile: <source UUID>.exr-source.exr` and `exrView: { part, group, levelX, levelY, encoding?, depthRange? }`. Source UUID is a resource identifier independent of layer UUID so multiple imported parts can reference one immutable EXR. The file preserves all original headers, parts, tile levels, channels and deep samples. `part` is an integer 0–63, `group` is a channel-name prefix, levels are integers 0–30, and the optional input encoding is a supported HDR space or `File color metadata`. Optional depth range is an ordered pair of finite numbers bounded to ±1e12. The selected part/group must exist in the retained header. These fields require version 16 and `hdrSourceFile`; its canonical TIFF and PNG cache hold the selected/composited two-dimensional preview. Source files are bounded to 256 MiB with validated headers, dimensions and references. Original-file export copies the EXR bytes; editing the two-dimensional derivative does not rewrite individual deep samples. Deep previews use depth-sorted front-to-back Over, with optional depth clipping. General overlapping-volume integration and arbitrary deep-sample editing are outside this format's preview semantics.

Windows/reference/mobile validators and native Mac source preserve these fields and resources. Versions 1–15 remain readable; readers older than version 16 reject new saves. Mac/iOS Xcode acceptance is tracked separately from shared-renderer tests.

Version 14 extends each editable filter with optional `maskFile`, `maskEnabled` and `opacity`. A mask's canonical filename is `<layer UUID>.<filter UUID>.filter-mask.png`, using uppercase UUIDs; it must be an embedded, ordinary 8-bit grayscale PNG. Every mask is included in asset validation and pixel budgets, including disabled masks. Its grid covers the normalized original-source box and follows the layer transform; a different grid resolution is bilinearly sampled at pixel centers. White applies the filter, black preserves the preceding stack result, and gray mixes them. `maskEnabled` defaults to true and requires `maskFile` when present. `opacity` defaults to 1 and must be finite in 0–1. The effective amount is mask coverage multiplied by opacity; original/filtered pixels blend using premultiplied alpha. Each filter uses the result of the preceding filter, retaining order. High-precision stacks mix in floating point before the final sixteen-bit quantization. Version-13 and earlier manifests cannot include any of these fields.

Cloning a layer changes the mask filename's layer UUID. Applying a filter preset or recorded stack allocates fresh filter UUIDs and mask filenames, retaining normalized mask geometry. Presets/actions carry the mask bytes in their local library payload. Pixel edits that bake the stack remove its source, filter parameters and mask references; undo retains the earlier resources. Project recovery, normal-save history fingerprints and portable archives include every referenced filter mask. Unchanged opening/applying preserves caches and parameters. Older readers reject version 14 rather than ignore the new masks.

Version 13 adds `vectorPath` on image layers and `vectorMask` on layers with an existing `maskFile` cache. Each uses `{ contours, fillRule, fill, stroke, strokeWidth }`. A contour has Boolean `closed` and `nodes`; every node has `point: [x, y]` and optional `incoming`/`outgoing` control points. Coordinates are relative to the layer box for paths, or `maskPlacement ?? transform` for masks; every coordinate is finite and between −4 and 4. A segment uses the previous node's outgoing handle and next node's incoming handle, defaulting absent handles to their anchors. The last segment returns to the first anchor only for closed contours. Paths allow at most 64 contours and 4,096 total nodes; open contours require two nodes, closed contours three. `fillRule` is `evenodd` or `nonzero`. Fill/stroke colors carry finite `red`, `green`, `blue` channels in 0–1; either may be null. `strokeWidth` is a finite fraction of the box's shorter side, in 0–1. A path needs a fill or a nonzero stroke. `vectorPath` cannot coexist with group, text, shape, adjustment-layer or editable-filter metadata.

Vector masks require all contours closed, a white fill, no stroke, and zero stroke width. Their grayscale PNG cache remains in the ordinary `maskFile`; a vector mask replaces that layer's raster mask, and the existing mask placement, link and visibility fields still apply. Regular mask pixel operations remove its vector metadata. Ordinary layer pixel operations remove `vectorPath`. Geometry transforms, duplication, canvas resizing and unchanged opening/saving preserve the geometry. The native Mac source preserves vector metadata while the original image/mask cache remains unchanged; native pixel replacement invalidates it by image identity. Native node authoring is not implemented yet. Older clients reject version 13 instead of silently dropping path data.

Later fields are optional and not gated on the version, so older readers ignore them and keep the pixels or the linked mask as they were:

- `maskPlacement` and `maskLinked`: an unlinked mask (`maskLinked` false; missing means linked) keeps its own transform in `maskPlacement`, a document-space rectangle like the layer transform, and no longer follows the layer when it moves. Both require a `maskFile`.
- `shape`: a layer made with the Shape tool keeps its style (`kind`, `red`/`green`/`blue`, `cornerRadius` in document pixels, and for lines `lineWidth` plus `start` and `end` as fractions of the layer box) so it redraws cleanly when scaled. Its PNG is still an ordinary raster; once anything else changes those pixels the metadata is dropped.

### Editable text

Pixel layer records may include optional `text` metadata: content, PostScript font name, font size in pixels, RGB color, alignment, tracking, line spacing and optional `boxSize` paragraph bounds. Text wraps inside these bounds; changing them reflows the text without scaling the font. The PNG remains the display and export fallback. Older readers ignore this metadata. Transforms, duplication, masks and canvas-size changes preserve it; destructive pixel operations rasterize text and omit the metadata on the next save. Missing fonts use the system font when edited, while the saved PNG preserves the original appearance until then. From version 10, optional `colorRuns` lists letters painted in another color than the text's own `red`/`green`/`blue`: each run has `location` and `length` in UTF-16 units of the content, plus `red`, `green` and `blue` (0–1). From version 11, optional `fontRuns` lists letters set in another face than `fontName`: the same `location` and `length`, plus `fontName`. Runs of either kind are sorted, do not overlap, have a positive length and end within the content; letters outside every run use the text's color or face.

### Layer effects

An optional `effects` record contains independent `stroke`, `shadow`, `colorOverlay`, `innerShadow`, `outerGlow` and `innerGlow` records. Stroke carries a size (0–500 layer pixels), a color, an opacity and an `inside` flag choosing which side of the edge it sits on; drop shadow and inner shadow each carry an angle, a distance, a blur, a color and an opacity; color overlay carries a color and an opacity; outer glow and inner glow each carry a size (0–500 layer pixels), a color and an opacity. Each supports optional `enabled` visibility (missing means visible); hidden effects keep all parameters and remain listed under their layer. Effects, including their visibility, are saved and participate in document undo. Canvas previews run on a serial background worker with a shared pixel budget; exports render the full-resolution effects. A record omitting an effect means that layer does not have it, so older readers see the effects they understand and ignore the rest.
