# OpenEXR and HDR in preview 0.10.0

Windows and the shared Android/iOS editor support PIZ, tiled and multipart EXR plus retained Deep scanline/tiled sources. Use **Image → Import OpenEXR**, **HDR working space**, **Deep EXR preview**, **Export OpenEXR** and **Export original OpenEXR**. New controls have English and Simplified Chinese translations.

## Import and editing

The decoder uses the official OpenEXR **3.4.16** library compiled to WebAssembly. It reads HALF/FLOAT RGB/RGBA or grayscale Y, including ZIP, ZIPS, None, RLE, PIZ, PXR24, B44/B44A and DWAA/DWAB. UINT color channels and Y/RY/BY chroma conversion are not implemented by this editor; auxiliary channels stay in the original file. Tile levels can be selected; mipmap X/Y levels must match, and the requested level must exist. Non-square pixels are rejected. Compression/type interpretation is checked by the [official library](https://openexr.com/en/latest/ReadingAndWritingImageFiles.html).

For multipart files, select a named part/pass or import all image parts. All-parts import uses each part's main RGB/Y pass. It validates/prepares all selected images before making one undoable import. The parts share a single immutable EXR resource. Other channels, passes and tile levels remain in that file, even when they are not displayed.

Display-window import retains original placement; selected lower tile levels scale back to the full data-window bounds. Data-window import uses the selected level's pixel dimensions. Source/display bounds are limited to 4 MP on phones or 16 MP on desktop; tiles are limited to 1024 pixels per side. Deep decoding is limited to 4 MP, 4096 samples per pixel and 8 million total samples on desktop or 1 million on phones. The existing combined resource limits and 128 MiB phone archive limit still apply. Files are limited to 256 MiB, with the phone's ordinary file picker applying its stricter 128 MiB limit.

Deep previews require RGB/Y, Z and A channels. Samples are stably sorted by Z and composited with front-to-back Over. Near/far depth controls recompute the selected two-dimensional derivative as an undoable step. Empty pixels and fractional coverage are supported. This is surface-sample preview composition; overlapping-volume integration, per-sample sculpting and volumetric relighting are not implemented. The original deep data remains intact. Premultiplied zero-alpha emission cannot be represented by the current straight-alpha editing surface and is rejected rather than erased. RGB must be finite within ±1,000,000 and alpha within 0–1.

## Working space and display

HDR editing is no longer restricted to linear sRGB. Choose **Linear sRGB**, **Linear Rec.2020**, **Linear P3-D65**, **ACEScg** or **ACES2065-1**. Input `colorInteropID`/chromaticities are interpreted or explicitly overridden, and linear matrices with Bradford adaptation convert between spaces. Existing source files remain in their own declared space; changing document space changes composition/adjustment-layer calculations without rewriting their samples. Individual editable filter stacks retain their source space. This is not a configurable OCIO pipeline, ACES view transform or general floating-point ICC/CMYK editor. Presets follow the [ASWF recommendation](https://github.com/AcademySoftwareFoundation/ColorInterop/blob/main/Recommendations/01_TextureAssetColorSpaces/TextureAssetColorSpaces.md).

**HDR display preview → Display output** offers Auto/HDR/SDR. On a display reporting high dynamic range and a browser/WebView supporting an extended `rgba16float` WebGPU canvas, the editor renders Display-P3 output with brightness above reference white. It checks the accepted canvas configuration and bypasses SDR Reinhard/Clip mapping for this output. The shader composites transparency over the checkerboard, converts linear values to extended sRGB encoding and writes an opaque floating-point target, following the [WebGPU extended-output model](https://gpuweb.github.io/gpuweb/). Preview exposure affects display brightness. GPU/display/API failure or an SDR device uses the SDR preview; SDR can also be selected explicitly. Preview settings never affect exported radiance. Physical brightness and headroom remain controlled by the OS, browser and display. The Windows GPU shader/readback test verifies values above one; actual HDR phone/Mac screen acceptance still requires the user's device.

This display implementation belongs to the shared editor, including mobile WebViews and browser use on a Mac. The original SwiftUI Mac app preserves the new sources/settings but still renders its existing PNG cache; it has not gained the shared WebGPU display or complete native EXR controls. Native Mac/iOS Xcode acceptance remains separate.

## Export and persistence

Export supports FLOAT32/HALF16, the listed compression methods, scanline/tiled output and a flattened composite or visible layers as multipart images. Layer parts include their group masks/opacity and honor inherited visibility. Use flattened output for clipping stacks. Multipart delivery is bounded to 16 MP total on desktop or 4 MP on phones. HALF has lower precision and a ±65504 range; overflow and nonzero color with underflowed alpha are rejected. PXR24/B44/DWA are lossy where defined by OpenEXR; PIZ/ZIP/ZIPS/None/RLE are lossless. Chromaticities and color IDs are regenerated consistently for the chosen output space.

**Export original OpenEXR** returns the retained file byte-for-byte, including every Deep sample and all parts/metadata. Two-dimensional edits are delivered through ordinary composite/layer export; they do not rewrite individual samples in that original file. Cached PNGs remain SDR derivatives. Files using the ACES2065-1 color space are not automatically declared compliant ACES containers.

New saves use **project format 16**, documented in [project-format.md](project-format.md). Windows, reference/mobile archives and native Mac source preserve `hdrWorkingSpace`, display mode, canonical float source space, retained EXR bytes and selected part/group/level/depth range. Versions 1–15 remain readable; older readers reject version-16 saves.

The packaged runtime adds about 0.75 MiB before ZIP compression and does not include Python, Node or the build toolchain. Rebuild instructions and pinned dependency/binary hashes are in `desktop/scripts/build-exr.ps1` and `desktop/native/exr/runtime.json`. Ordinary asset builds verify and copy the supplied prebuilt runtime. EXR parsing/color/codec work runs in cancelable workers; source/sample/header/heap budgets remain enforced.

## Verification

Reference fixtures are generated using the official OpenEXR 3.4.16 Python wheel and a standalone official C++ deep-tiled writer (`desktop/tests/openexr-deep-fixture.cpp`). The native Python library independently checks the deep samples and application exports. Tests cover partial tiles, named multipart images, deep sorting/range composition, source conservation, archive/native-store round trips, working-space changes, original export, UI language and SDR fallback. [verification-0.10.0.md](verification-0.10.0.md) records the release results and hardware acceptance boundaries.
